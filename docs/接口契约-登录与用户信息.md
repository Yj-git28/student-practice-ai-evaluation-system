# 2.14　第 14 步：接口契约

> 本节定义前端守卫与登录页依赖的两个接口：登录换 token、取用户信息与权限。所有字段以后端 `auth` 包现有实现为准，代码与本文不一致时先改代码或同步改本文，不允许前后端各写一套。

## 2.14.1　通用约定

| 项目 | 约定 |
|---|---|
| 基准路径 | `/api`（前端 axios `baseURL: '/api'`），本文路径均从此开始 |
| 请求体格式 | `Content-Type: application/json`，UTF-8 |
| 响应包装 | 统一 `R<T>`：`{ "code": int, "msg": string, "data": T }` |
| 成功码 | `code = 200`，`msg = "ok"`（`R.ok()` 固定输出 200，不是 1） |
| 业务失败 | HTTP 200 + `data: null` + 业务码（如 `4001`），由 `GlobalExceptionHandler` 统一包装 |
| 鉴权失败 | HTTP 401 / 403，同时 body 中 `code` 也写 401 / 403，body 与状态码双写 |
| 鉴权方式 | 请求头 `Authorization: Bearer <token>` |
| token 有效期 | 28800 秒（8 小时），由 `app.jwt.expire-seconds` 配置 |

## 2.14.2　登录

### 基本信息

| 项目 | 内容 |
|---|---|
| 方法 / 路径 | `POST /api/auth/login` |
| 鉴权 | 否，白名单接口（`SecurityConfig` 中 `permitAll`） |
| 对应实现 | `AuthController#login` → `AuthService#login` → `LoginDTO` / `LoginVO` |

### 请求参数

```json
{
  "username": "teacher01",
  "password": "123456"
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| username | string | 是 | 登录名，对应 `sys_user.username`，唯一 |
| password | string | 是 | 明文密码，后端用 BCrypt 与库中密文比对，前端不做加密 |

### 成功响应

```json
{
  "code": 200,
  "msg": "ok",
  "data": {
    "token": "eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxIiwi...",
    "expiresIn": 28800
  }
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| code | int | 200 表示登录成功 |
| data.token | string | JWT，HS256 签名；载荷含 `sub`（用户 ID 字符串）、`username`、`role`，以及 `iat` / `exp` |
| data.expiresIn | long | token 有效秒数，供前端计算过期时间或提示 |

### 失败响应

| 场景 | HTTP 状态 | body |
|---|---|---|
| 用户名不存在 | 200 | `{ "code": 4001, "msg": "用户名或密码错误", "data": null }` |
| 密码不匹配 | 200 | `{ "code": 4001, "msg": "用户名或密码错误", "data": null }` |
| 用户未绑定角色 / 角色权限缺失 | 200 | `{ "code": 500, "msg": "服务器内部错误", "data": null }`（`buildLoginUser` 抛非业务异常时的兜底） |

> 用户名错误与密码错误统一返回 4001 且文案相同，避免被枚举出账号是否存在。

### 调用示例

```bash
curl -X POST http://localhost:8080/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"teacher01","password":"123456"}'
```

## 2.14.3　取用户信息与权限

### 基本信息

| 项目 | 内容 |
|---|---|
| 方法 / 路径 | `GET /api/auth/getInfo` |
| 鉴权 | 是，需 `Authorization: Bearer <token>`；方法上标 `@PreAuthorize("isAuthenticated()")`，只要求已登录、不要求具体权限码 |
| 触发时机 | 登录成功后由前端路由守卫调用一次，结果缓存在 Pinia，后续页面从 store 读权限 |
| 对应实现 | `AuthController#getInfo` → `AuthService#getInfo` → `UserInfoVO` + `PermissionService` |

### 请求头

```
GET /api/auth/getInfo
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...
```

无请求参数。

### 顶层字段

| 字段 | 类型 | 来源 / 说明 |
|---|---|---|
| userId | number | `sys_user.user_id` |
| username | string | `sys_user.username` |
| realName | string | `sys_user.real_name`，前端页面右上角展示用 |
| roleId | number | `sys_user.role_id`，单角色外键 |
| roleCode | string | `sys_role.role_code`，取值 `TEACHER` / `STUDENT` / `ADMIN`，程序判断用这个，不要用 roleName 做逻辑 |
| roleName | string | `sys_role.role_name`，仅展示 |
| classId | number \| null | `sys_user.class_id`，学生有值、教师与管理员为 null |
| roles | string[] | 角色码数组，当前恒为单元素 `[roleCode]`，保留数组是为了后续扩展多角色 |
| permissions | string[] | 该用户被授予的全部 `perm_code`，含菜单与按钮两类，前端按钮级鉴权只认这个数组 |
| dataScope | string | 数据范围，`ADMIN → ALL`、`TEACHER → TEACHER_SELF`、其他 → `STUDENT_SELF`；库中无该字段，由角色码统一映射 |
| menus | object[] | 菜单树，根节点为 `parentId = 0` 或父节点未被授权的“孤儿节点” |

### menus 节点字段

| 字段 | 类型 | 说明 |
|---|---|---|
| permissionId | number | `sys_permission.permission_id` |
| parentId | number | `sys_permission.parent_id`，根节点为 0 |
| permName | string | 菜单显示名 |
| permType | number | **只含 1（菜单）**；按钮类（2）不进 menus，只走 permissions |
| permCode | string | 权限码，与 permissions 中的取值一致 |
| permPath | string | 前端 `router` 的 `path`，菜单类必有值且必须与前端路由一一对应 |
| icon | string \| null | 图标名，可空 |
| sort | number | 同级排序，前端按升序渲染 |
| children | object[] | 子菜单数组，无子节点时为 `[]`，不是 `null` |

### 规则说明

1. `menus` 只取 `perm_type = 1`，按钮权限一律通过 `permissions` 数组下发，**不要把按钮塞进 menus 当路由用**。
2. 树的构建规则：`parentId = 0` 为根；若某节点的父节点未被授权（不在返回集合内），该节点提升为根，避免菜单整块消失。
3. `permissions` 与 `menus` 的 `permCode` 有交集但不是子集关系：菜单码用于路由准入，按钮码用于按钮显隐。
4. 同一次请求内 `permissions` 顺序按 `LinkedHashSet` 去重保序，前端不要依赖顺序做逻辑。
5. 用户信息以数据库与 Redis 缓存（`PermissionCacheService`）为准，token 中的 `role` 仅作日志与排障参考，鉴权不做依据。

### 失败响应

| 场景 | HTTP 状态 | body |
|---|---|---|
| 未带 token | 401 | `{ "code": 401, "msg": "未登录或登录已过期", "data": null }` |
| token 签名错误 / 已过期 / 格式非法 | 401 | 同上 |
| 已登录但权限不足（后续加 `@PreAuthorize` 的接口） | 403 | `{ "code": 403, "msg": "没有访问权限", "data": null }` |

## 2.14.4　前端对接要点

| 环节 | 做法 |
|---|---|
| 登录页 | `POST /auth/login`（`baseURL` 已含 `/api`，**不要再补 `/api`**），成功后 `setToken(data.token)` 写 localStorage 与 store |
| 守卫 | `router.beforeEach` 中有 token但 store 无用户信息时调 `GET /auth/getInfo`，失败清 token 跳登录 |
| 响应拦截 | `utils/request.js` 已 `return res.data`，即拿到的是 `R` 包装体，业务判断用 `res.code === 200`，不再看 `res.status` |
| 按钮显隐 | 用 `userStore.userInfo.permissions.includes('training:publish')`，或封装 `v-perm` 指令 |
| 菜单渲染 | 用 `userStore.userInfo.menus` 递归渲染侧边栏，路径取 `permPath`，不要继续用 LayoutMain 里的三段 `v-if` |
| 角色判断 | 用 `roleCode`，不要用 `role` 字段名 |

## 2.14.5　后端实现位置

| 文件 | 作用 |
|---|---|
| `auth/AuthController.java` | 两个接口的入口，`login` 标 `@PublicApi`，`getInfo` 标 `@PreAuthorize("isAuthenticated()")` |
| `auth/AuthService.java` | 登录校验、组装 `UserInfoVO`、菜单树构建 |
| `auth/LoginDTO.java` / `auth/LoginVO.java` | 登录出入参 |
| `auth/UserInfoVO.java` | 用户信息与权限出参 |
| `security/JwtService.java` | 签发与解析 token，HS256，key 需 ≥ 32 字节 |
| `security/JwtAuthFilter.java` | 解析 header 中的 Bearer token，失败按 401 |
| `system/service/PermissionService.java` | 组装 `LoginUser`、查询菜单、`dataScope` 映射、缓存失效 |
| `common/R.java` / `common/GlobalExceptionHandler.java` | 统一响应体与业务异常包装 |

## 2.14.6　待确认事项

| 编号 | 事项 | 影响 | 处理建议 |
|---|---|---|---|
| Q1 | 成功码不统一：本文按代码实现写 `200`，接口文档 2.2 规定成功为 `1` | 前端判断逻辑二选一，混用必出错 | 由文档负责人拍板，全组只留一种；建议改文档为 200（与代码一致，改动最小） |
| Q2 | `SysPermission` 实体当前无 `children` 字段，但 `AuthService.buildTree` 调用了 `setChildren` | 后端编译不通过 | 在实体补 `private List<SysPermission> children;` 及 getter/setter，或改 `buildTree` 为返回 `Map` 结构 |
| Q3 | 前端 `useUserStore` 用 `info.role` 存角色，后端返回的是 `roleCode` | 角色判断恒为空 | store 改读 `roleCode`，并在 `setUserInfo` 里同时保留 `roleCode` 与 `roleName` |
| Q4 | `sys_user` 实库无 `status` 字段 | 无法做禁用账号 | 契约暂不下发 status，后续加列再补字段 |
| Q5 | `sys_role_permission` 主键与时间字段未确认 | 权限分配 SQL 可能写错 | 开发前执行 `DESC sys_role_permission` 确认并回写本文 |
| Q6 | 登录失败返回 HTTP 200 + 业务码 4001 | 前端若只看 HTTP 状态会误判成功 | 已在 2.14.4 明确用 `code` 判断，联调时按此执行 |
